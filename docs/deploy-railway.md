# Развёртывание на Railway

## Схема

Один проект Railway, в нём три сервиса:

| Сервис | Откуда | Что делает |
|---|---|---|
| `Postgres` | база Railway (Database → PostgreSQL) | данные |
| `api` | репозиторий `PMS-CRM_backend` | API: `Dockerfile` и `railway.json` в корне репозитория |
| `web` | репозиторий `PMS-CRM` | веб: nginx отдаёт приложение и проксирует `/api` на `api` |

Браузер ходит только на домен веба, а nginx веба передаёт `/api` в сервис
`api` по внутренней сети Railway. Из этого следует:

- Фронту не нужен `API_URL` на этапе сборки: все адреса в коде относительные
  (`/api/...`). Веб знает, куда проксировать, из переменной `API_UPSTREAM`.
- CORS не участвует: для браузера веб и API - один адрес.
- Cookie обновления сессии (httpOnly, SameSite=Strict) работает. Если раздать
  веб и API на разных доменах `*.up.railway.app`, браузер посчитает их разными
  сайтами, cookie не дойдёт, и вход будет слетать при каждом обновлении страницы.

Сервисы должны быть в **одном** проекте: ссылки на переменные
`${{сервис.ПЕРЕМЕННАЯ}}` и внутренняя сеть `*.railway.internal` работают только
внутри проекта. Ниже в ссылках сервисы названы `Postgres`, `api` и `web`; если
у вас они называются иначе, впишите свои имена.

## Шаги

Порядок важен: `PUBLIC_API_URL` у `api` ссылается на домен веба. Пока домена
нет, ссылка пустая, и API не стартует (адрес не проходит проверку конфигурации).

1. **New Project → Database → PostgreSQL.**
2. **New → GitHub Repo → PMS-CRM**, сервис назвать `web`.
   - Variables - таблица ниже.
   - Networking → Generate Domain на порт `8080` (переменная `PORT`).
3. **New → GitHub Repo → PMS-CRM_backend**, сервис назвать `api`.
   - Variables - таблица ниже.
   - Volume: подключить к `api` с путём `/data`. Без тома сканы документов и
     фото пропадают при каждом деплое.
   - Публичный домен API не нужен (можно включить, чтобы открыть `/api/docs`).
4. Когда `api` задеплоился, передеплоить `web` (Redeploy), чтобы его
   `API_UPSTREAM` взял адрес `api`. Открыть домен веба: на пустой базе откроется
   регистрация гостиницы и её владельца.

### Переменные `api`

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |
| `JWT_SECRET` | случайная строка от 48 символов (кнопка Generate) |
| `PORT` | `4000` |
| `HOST` | `::` - внутренняя сеть Railway бывает только IPv6 |
| `MIGRATE_ON_START` | `true` - миграции при каждом старте, под блокировкой |
| `SEED_DEMO_IF_EMPTY` | `true` только для стенда показа: демо в пустую базу при первом старте |
| `COOKIE_SECURE` | `true` |
| `PUBLIC_API_URL` | `https://${{web.RAILWAY_PUBLIC_DOMAIN}}` - ссылки на файлы строятся от адреса веба |
| `CORS_ORIGINS` | `https://${{web.RAILWAY_PUBLIC_DOMAIN}}` |
| `REQUIRE_TOTP_FOR_PRIVILEGED` | `true`; для демо - `false` |
| `FILES_DIR` | `/data/files` |
| `RAILWAY_RUN_UID` | `0` - том принадлежит root, а образ работает не от root |

### Переменные `web`

| Переменная | Значение |
|---|---|
| `API_UPSTREAM` | `http://${{api.RAILWAY_PRIVATE_DOMAIN}}:${{api.PORT}}` |
| `PORT` | `8080` (на этот порт и генерируется домен) |
| `VITE_DEMO` | `true` - только для презентации: на входе выбор демо-сотрудника |

## Если веб и API всё же в разных проектах

Ссылки между проектами не работают, адреса вписываются руками, а запросы
веб → API идут через интернет:

- у `api` включить публичный домен;
- `web`: `API_UPSTREAM=https://<домен api>` (nginx сам передаст правильное имя
  хоста и SNI);
- `api`: `PUBLIC_API_URL` и `CORS_ORIGINS` = `https://<домен web>`.

## Демо-данные

Проще всего - `SEED_DEMO_IF_EMPTY=true` у `api`: при первом старте на пустой
базе API сам положит демо-гостиницу (номера, брони, гостей, смены, сотрудников).
В базу, где уже есть гостиница, сид ничего не пишет. Пароль демо-сотрудников
общий и известный, поэтому после показа базу пересоздают, а переменную ставят
`false`.

Вручную, с локальной машины, взяв `DATABASE_PUBLIC_URL` у сервиса `Postgres`:

```bash
cd backend
DATABASE_URL="<DATABASE_PUBLIC_URL>" pnpm db:seed
```

Пароль демо-сотрудников `demo12345`, PIN `1234`.

## Обновления

- Веб: пуш в `PMS-CRM` (ветка `main`) - Railway пересобирает `web`. Правки только
  в `backend/` его не трогают (`watchPatterns` в `railway.json`).
- API: правки делаются в `backend/` монорепозитория, затем
  `pnpm backend:push` (это `git subtree push --prefix=backend backend main`) -
  Railway пересобирает `api`. В `PMS-CRM_backend` напрямую не коммитить: это
  зеркало, следующий `subtree push` с ним разойдётся.

## Проверка после деплоя

- `https://<домен web>/healthz` → `ok`
- `https://<домен web>/api/v1/setup` → `{"needed":true}` на пустой базе
- вход и выход, загрузка скана документа при заселении (проверка тома)
- две вкладки: бронь, созданная в одной, сама появляется в другой (поток
  событий через прокси)
